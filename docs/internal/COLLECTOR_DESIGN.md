# 성능 메트릭 수집기 설계 (운영자 내부)

> 대상: 대시보드 운영자 · 케이스 A~C 엔진 `/metrics` **검증용 스크랩** 수집기의 내부 설계
> 용도 변경(DECISIONS #23): 스크랩 값은 1차 수집이 아니라 **자기신고 serving 블록의 교차 검증 기준**이다 — 설계·함정은 동일하게 적용된다
> 서비스 담당자 계약([구현 스펙](../METRICS_COLLECTION_SPEC.md))에는 영향 없음 — 담당자 요구사항은 "metricsUrl(VIP) 제출 + 방화벽 개방" 그대로다.
> 관련 결정: [DECISIONS #16](DECISIONS.md)

---

## 1. 문제 정의 — /metrics는 "누적 계량기"다

추론 엔진의 `/metrics`는 현재 상태가 아니라 **프로세스 시작 이후의 누적값**(카운터·히스토그램 버킷)만 노출한다. daily 집계는 "누적값의 하루치 증가분"을 구하는 빼기 연산인데, 이 빼기에 네 가지 함정이 있다:

| # | 함정 | 내용 |
|---|---|---|
| 1 | **counter reset** | 엔진 재시작 시 누적값이 0으로 리셋 — 자정 스냅샷 2개로 빼면 음수/유실. 리셋 전 마지막 값을 목격해둬야 이어붙일 수 있다 |
| 2 | **주기 수집 필요** | 1을 풀려면 daily 결과라도 분 단위로 긁어 쌓아야 한다 (하루 1회 GET은 재배포 있는 날마다 조용히 틀림) |
| 3 | **버킷 선(先)합산** | percentile은 평균·재조합 불가 — 레플리카·구간의 히스토그램 버킷을 먼저 합산하고 percentile은 마지막에 1회만 |
| 4 | **quantile 보간** | 버킷은 구간 개수만 알므로 p99는 버킷 경계 보간으로 근사 — 보간 규칙의 정확성 책임 |

## 2. 제약 조건 (사내 환경)

- **접근은 LB VIP 하나** — 방화벽이 VIP 단위로 열리고 파드 주소는 재기동마다 바뀌므로, 레플리카 개별 접근은 요구할 수 없다
- **배포 방식 통제 불가** — 서비스팀이 다수이고 재배포·스케일링 방식이 제각각. 종료 유예(preStop) 등은 강제 불가
- **담당자 추가 부담 0 유지** — 스크랩 성립을 위해 서비스 코드·설정 변경을 요구하지 않는다

## 3. 설계 — VIP 경유 역다중화(demux) 수집

### 성립 근거 두 가지

1. **누적 카운터는 희소 관측에 무손실이다.** 레플리카 X를 09:00(누적 1,000)에 보고 17:00(누적 51,000)에 다시 보면 델타 50,000 — 사이를 못 봐도 유실이 없다. 유실은 오직 "마지막 목격 이후 죽은 경우"에만 발생한다. 따라서 매 스크랩마다 모든 레플리카를 볼 필요가 없고, LB가 요청을 아무렇게나 분산해도 각 레플리카를 "가끔" 만나면 충분하다.
2. **응답마다 응답자를 지문으로 식별할 수 있다.** Prometheus 클라이언트가 기본 노출하는 `process_start_time_seconds`가 레플리카×세대의 고유 키다. 재시작하면 값이 바뀌므로 리셋 감지까지 겸한다 ("값이 줄었나" 휴리스틱보다 확정적 — 자정 직후 재시작처럼 새 카운터가 옛 값을 금방 추월하는 경우도 놓치지 않는다).

### 파이프라인

```
[VIP]  ← 담당자 제출값 그대로
  │  10~30초 주기 · 매 스크랩 새 TCP 연결(keepalive 끔 — LB가 분산하도록) · 타임아웃/재시도
  ▼
[응답 파싱] → process_start_time으로 레플리카 스트림 분류 (역다중화)
  ▼
[스트림별 델타 누적기]
  │   같은 start_time → delta = new − last
  │   새 start_time   → 새 세대 시작, delta = new (0부터 다시 센 분량)
  ▼
[DB: 분 단위 델타 적재 · 14일 보관]  ← backfill 창(14일)과 일치, daily 재계산 멱등
  ▼
[daily 배치] Σ델타 → 전 스트림 버킷 합산 → percentile 보간 1회
  ▼
[검증·품질 플래그] → 대시보드 표시
```

- 커버리지 수치 감: 레플리카 R대, 15초 주기면 각 레플리카를 평균 R×15초마다 목격 (R=8 → ~2분)
- 트래픽이 큰 서비스는 주기를 적응적으로 단축 (유실 상한이 비례해 줄어듦)
- 엔진별 메트릭명 차이는 매핑표(스펙 케이스 C)로 흡수 — 수집기는 매핑표를 설정으로 읽는다. 엔진 버전 변경은 `/v1/metrics`의 `engine` 자기신고로 감지해 매핑 갱신 필요 여부를 알림

## 4. 정합성 검증 — "이상은 시스템이 잡는다"

이 체계는 같은 값을 재는 **독립 소스(기존 토큰 API)** 를 이미 갖고 있어 교차 검증이 공짜다:

| 검증 | 방법 | 잡아내는 것 |
|---|---|---|
| **토큰 교차 검증** | 엔진 생성 토큰 카운터의 하루 증가분 ≈ 토큰 API outputTokens (오차 임계 초과 시 알림) | 리셋 보정 실패, 레플리카 누락, affinity 오염 등 수집 사고 전반 |
| **성능 교차 검증** | 스크랩 히스토그램에서 산출한 percentile ≈ 자기신고 serving 값 (오차 임계 초과 시 알림) | 서비스측 집계 실수 — 레플리카별 percentile 평균, 리셋 유실 |
| 커버리지 | 성공 스크랩 수 ÷ 계획 스크랩 수 | 네트워크 단절, URL 변경 후 시트 미갱신 |
| 리셋 계량 | 하루 리셋 횟수 × 스크랩 간격 × 직전 처리율 = **유실 상한** 기록 | 불안정 배포 패턴 (담당자 알림 소재) |
| **affinity 감지** | 하루 동안 관측된 start_time 종류 수가 1인데 gpuCount·트래픽은 다수 레플리카 규모 | source-IP 고정 LB — 해당 팀과만 개별 협의 (전사 요구 아님) |

**품질 플래그**: 각 daily 성능 값에 `정상 / 부분 데이터(커버리지 미달) / 검증 실패`를 부착해 대시보드에 표시한다. 정합성의 목표는 "100% 정확"이 아니라 **"틀렸을 때 틀렸다고 표시됨"** 이다.

## 5. 유실 모델 (오차 상한)

| 리셋 원인 | 유실 |
|---|---|
| 계획 재시작 (롤링 배포 — 대부분) | 마지막 목격 이후 ~수 분치 × 해당 레플리카 1대분. 배포에 종료 유예(§6)가 있으면 **0** |
| 크래시 (OOM·노드 장애 — 드묾) | 상동 (원리적 한계 — 어떤 수집기도 동일) |
| affinity LB | 감지 → 개별 협의 전까지 해당 서비스는 품질 플래그 "검증 실패" |

## 6. 엔진·배포측 선택 사항 (요구 아님 — 온보딩 가이드에 "하면 좋은 것"으로만)

- **종료 유예**: 배포 템플릿에 `preStop: sleep 45` + terminationGracePeriod ≥ 60s — 계획 재시작의 유실이 0이 된다. 다수 팀이 LB 드레인용으로 이미 쓰는 설정이라 비용이 낮지만, **강제하지 않는다** (없어도 시스템은 성립하고 유실이 계량될 뿐)
- 레플리카 고유 라벨(instance id) 노출 — 지문이 더 확정적이 되지만 start_time만으로 충분

## 7. 구현 선택지

| 선택지 | 평가 |
|---|---|
| 경량 기성 수집기 (Prometheus agent mode, vmagent, Grafana Alloy) + 쿼리 | 함정 1·2를 검증된 코드로 해결, 3·4는 쿼리 함수 제공. **역다중화 요건(매 스크랩 새 연결, 지문 분류)이 지원되는지 확인 필요** |
| custom 수집기 (본 설계) | 함정 1~4를 §3 설계대로 직접 구현 — 기존 크론·DB 인프라와 정합, 역다중화를 정확히 통제 가능. 파싱은 라이브러리 사용 |
| 하루 1회 GET | **금지** — 재배포 있는 날마다 조용히 틀린 percentile |

권고: **custom(§3 설계) 우선 검토** — VIP 역다중화라는 비표준 요건 때문에 기성품의 기본 동작(타깃별 시계열)과 맞지 않을 수 있고, 대시보드팀이 이미 수집 크론·DB를 운영하고 있어 "분 단위 델타 적재 → daily 배치" 패턴이 기존 인프라에 자연스럽다.
