## 1. 배경과 목적

토큰 대시보드는 현재 기존 토큰 API를 통해 **토큰 사용량·요청 수**를 daily로 수집하고 있다.
여기에 두 가지를 추가로 수집하여 비용·효율·성능을 한 화면에서 보는 것이 목표다.

| 추가 수집 항목 | 목적 |
|---|---|
| **모델별 GPU Hour** (모델에 GPU가 매핑·할당된 시간) | 할당 비용의 용도 분해와 효율 산출 — 비용 자체는 GPU 대시보드의 할당 기준으로 산출 (§4.1) |
| **서비스 메트릭** (TTFT, ITL, Output TPS) | ① 비용의 분모 확보 → 원/1M토큰 산출<br>② 비용 변화 원인 분해 (트래픽 증가 vs 효율 저하)<br>③ 비용 조정 의사결정의 안전장치 (줄여도 되는가)<br>④ 공유 모델 비용 배부 근거 |

**설계 원칙**

1. **이중 소스 금지** — 기존 토큰 API가 이미 수집하는 값(토큰량, requests)은 다시 받지 않는다. 파생 가능한 값(일평균 RPS = requests ÷ 86,400 등)도 받지 않는다.
2. **기존 계약 상속** — 기존 토큰 API의 pull 방식·식별자·응답 규칙을 그대로 따른다. 담당자 학습 비용 최소화.
3. **담당자 부담 최소화** — 신규 구현은 서비스당 GET 엔드포인트 최대 1개. vLLM/SGLang 사용 팀은 서비스 메트릭 구현이 아예 불필요(§5.2).

### 1.1 용어 정의

본 문서와 관련 논의에서 아래 표기로 통일한다. 특히 "프록시"는 게이트웨이·외부 API 연동과 혼동을 일으키므로 사용하지 않는다.

| 용어 | 정의 |
|---|---|
| **추론 엔진** | vLLM, SGLang 등 모델을 실제 실행하는 서빙 소프트웨어. 서비스 메트릭의 기본 측정 위치 |
| **게이트웨이** | 서비스가 호출자 요청을 받아 추론 엔진 또는 외부·사내 API로 전달하는 자체 서버 계층. 엔진 측정이 불가할 때의 대체 측정 위치 |
| **LLM API 플랫폼 (플랫폼)** | 사내 GPU로 모델을 서빙하여 API로 제공하는 사내 서비스. 서비스 간 사용 관계의 "공급자" |
| **소비 서비스 (소비자)** | 플랫폼 API를 호출해 사용하는 사내 서비스 |
| **직접 사용자** | 서비스를 거치지 않고 개인 자격으로 플랫폼 API를 호출하는 사내 구성원 |
| **외부 API 연동 서비스** | 사내 GPU 없이 외부 상용 LLM API를 호출해 기능을 제공하는 서비스 (구 "API 프록시" — 본 문서에서 미사용) |
| **할당 (allocation)** | GPU 대시보드 기준으로 서비스에 배정된 GPU. **비용 발생의 기준** (§4.1) |
| **가동 (GPU Hour)** | **모델에 GPU가 매핑·할당된 시간.** `/v1/metrics`로 제공 (§4.1) |
| **배부** | 플랫폼에서 발생한 비용을 사용 실적(가중 토큰) 비율로 소비자에게 나누어 귀속시키는 것. 표시만 하는 **showback**과 실제 정산인 **chargeback**을 구분 |
| **정규 모델명 (canonical id)** | 취합본에 등재된 모델의 공식 표기. 모든 수집 데이터는 이 표기로 정규화된다 (§3.1) |
| **별칭 (alias)** | HF 경로, 체크포인트명, served-model-name, 외부 API 날짜 버전 등 canonical id로 매핑되는 그 외 모든 표기 |
| **체급 (sizeClass)** | 모델 규모 구분: S(~15B) / M(~40B) / L(40B+) — MoE는 활성 파라미터 기준. 효율 비교·랭킹의 격리 단위 (§8) |
| **취합본** | §3.2의 엑셀 양식으로 취합·관리되는 관리 정보의 정본 (서비스·모델 표기, 매핑, 소비 관계 등) |

## 2. 전체 아키텍처

```
[중앙 수집기 (토큰 대시보드측), 매일 새벽 크론]
   │
   ├─ (기존) GET {service}/v1/usage?date=어제      ← 토큰·requests (기존 토큰 API)
   │
   ├─ (신규) GET {service}/v1/metrics?date=어제    ← GPU Hour (+ 비표준 엔진의 서비스 메트릭)
   │
   └─ (신규) 중앙 Prometheus가 vLLM/SGLang의 /metrics를 상시 스크랩
              → daily 집계 시 히스토그램에서 percentile 계산
```

- **방향은 pull.** 중앙 수집기가 매일 새벽 각 서비스의 GET 엔드포인트를 호출한다. 크론·재시도·장애 감지는 전부 중앙 책임. 서비스는 상태 없는 GET만 제공한다.
- 서비스 담당자가 구현·제공하는 것: ① `/v1/metrics` GET 엔드포인트 1개, ② (vLLM/SGLang인 경우) `/metrics` URL 제출 및 네트워크 개방. 끝.

## 3. 식별자와 계층 구조

기존 토큰 API와 **동일한 식별자**를 사용한다. 이 일치가 토큰↔GPU↔성능 데이터 JOIN의 성립 조건이다.

```
serviceGroup (서비스그룹/과제)  예: claude
  └─ service (서비스)           예: claude-cowork     ← 수집·제공 단위
       └─ model (모델)          예: opus
```

- **수집·제공 단위는 service.** serviceGroup은 대시보드에서 하위 service들을 합산(rollup)해 보여주는 뷰이며, 데이터를 직접 제공하지 않는다.
- 하위 service 어디에도 귀속되지 않는 그룹 공통 GPU가 있는 경우, 그룹 명의의 별도 service(예: `claude-shared`)로 등록해 제공한다. 1단계에서는 하위 배부 없이 "그룹 공통" 행으로 표시한다.
- `model`은 필수. `"unknown"`은 **test 카테고리에서만 허용**한다 — 프로덕션(serving/standby)에서 "무슨 모델인지 모른다"는 성립하지 않으며, unknown이면 모델별 분해·배부·효율 산출이 전부 불가능해진다(§4.1 정합성 검증). 기존 토큰 API의 unknown은 레거시 로깅 호환이고, 신규 metrics API는 처음 만드는 계약이므로 이 규칙을 적용한다.
- **표기 통일**: (serviceGroup, service, model)의 공식 표기 목록을 중앙이 취합본으로 관리한다(§3.2). 기존 토큰 API와 신규 metrics API가 반드시 같은 문자열을 사용해야 한다. (`claude` vs `Claude` 불일치 시 JOIN 실패)

### 3.1 모델명 정규화 — canonical model id

**문제는 양방향이다.** 같은 모델이 출처마다 다르게 불리기도 하고(표기 난립), 서로 다른 모델이 같은 이름으로 불리기도 한다(뭉침). 한 줄 원칙:

> **다르게 불리는 같은 것은 합치고, 같게 불리는 다른 것은 나눈다.**

사례로 보면:

| 사례 | 상황 | 처리 | 이유 |
|---|---|---|---|
| ① 표기만 다른 같은 모델 | A팀은 `meta-llama/Llama-3.3-70B-Instruct`, B팀은 `/models/llama33-70b` — 둘 다 순정 동일 웨이트 | **합침**: canonical `llama3.3-70b` 하나, 두 표기는 alias | 모델별 요약에서 합산하는 게 맞는 경우 |
| ② 같은 이름의 다른 모델 | A팀은 순정, B팀은 자체 파인튜닝본 — 둘 다 그냥 "llama3-70b"라 부름 | **나눔**: `llama3.3-70b` vs `llama3.3-70b-ft-cs` | 성능·효율이 다른데 묶이면 요약이 왜곡 |
| ③ 양자화 변형 | 같은 웨이트의 FP16 배포와 AWQ 배포 | **나눔**: `llama3.3-70b` vs `llama3.3-70b-awq` | GPU 효율이 크게 다름 |
| ④ 외부 API 날짜 버전 | `gpt-4o-2024-11-20`, `gpt-4o-2025-03-26` | **합침**: canonical `gpt-4o`, 날짜 문자열은 alias | 공급사 마이너 스냅샷까지 나누면 과분해 |

**나눌지 합칠지 판단 플로우** — 세 질문에 모두 "예"면 합치고, 하나라도 "아니오"면 나눈다:

1. 웨이트가 같은가? (같은 공개 모델의 같은 버전인가)
2. 파인튜닝 없는 순정인가? (사내 파인튜닝이면 무조건 별도)
3. 정밀도·양자화가 같은가?

**애매하면 나눈다 (비가역성 원칙).** 나눠 놓은 것은 family rollup으로 언제든 합쳐 볼 수 있지만, 한 id로 합쳐 쌓인 데이터는 나중에 분해할 수 없다.

**"모델별 요약" 현황판의 뭉침 위험과 3단 분해 표기**

서로 다른 서비스가 같은 canonical을 쓰면 모델별 요약에서 한 행으로 묶인다. 순정 동일 모델(사례 ①)이면 의도된 동작이지만, 사례 ②·③이 스며들면 요약이 오염된다. 방지책 두 가지:

- **사내 파인튜닝은 반드시 `-ft-{용도}` 접미로 별도 canonical.** 순정과 같은 id 사용을 금지한다 (취합 시 검증).
- **현황판을 modelFamily → canonical → service 3단 드릴다운으로 구성한다:**

```
modelFamily: llama3.3                  ← 최상단 rollup (합쳐 보기)
  ├─ canonical: llama3.3-70b            ← 요약 행 단위 (순정 FP16)
  │    ├─ service: doc-summary          ← 누가 쓰는지 분해
  │    └─ service: hr-chatbot
  ├─ canonical: llama3.3-70b-awq
  │    └─ service: chat-assistant
  └─ canonical: llama3.3-70b-ft-cs
       └─ service: cs-bot
```

같은 canonical 행을 펼치면 서비스별로 분해되므로, "이 모델의 전사 총량"과 "누가 얼마나 쓰는지"를 다 볼 수 있다. 같은 모델인데 서비스 간 원/1M토큰이 2배 차이 나는 것 같은 운영 노하우 격차도 이 분해에서 드러난다.

**운영 규칙**

- 표기 규칙: 소문자·하이픈, `{패밀리}{버전}-{크기}[-{변형}]`. 변형 접미: `-awq`/`-fp8` 등 양자화, `-ft-{용도}` 파인튜닝.
- 기존 토큰 API의 표기는 바꾸라고 요구하지 않고 alias로 흡수한다.
- 미등록 표기가 유입되면 `unknown`으로 뭉개지 않고 "미등록"으로 격리 + 담당자 알림 → 담당자 확인을 거쳐 canonical/alias 분류를 취합본에 반영한다 → 사전이 운영 중에 완성된다(§3.2 폐루프).
- vLLM/SGLang 팀은 `--served-model-name`을 canonical id로 설정하면 Prometheus 라벨이 처음부터 정규 표기로 나와 정규화가 불필요해진다.

### 3.2 관리 정보 취합 — 엑셀 (1단계)

**1단계에서는 별도 시스템·등록 화면 없이 엑셀 양식으로 취합한다.** 담당자는 온보딩 시 양식을 1회 작성해 제출하고, 변경이 생기면 갱신본을 제출한다. 취합 방식은 추후 변경될 수 있다(아래 "향후" 참조).

**취합 항목** (엑셀 양식):

| # | 항목 | 내용 |
|---|---|---|
| ① | 서비스 표기 | serviceGroup · service · 담당자(owner) |
| ② | 모델 표기 | canonical id + alias 목록 (+ modelFamily, **sizeClass**) |
| ③ | GPU 할당 매핑 | GPU 대시보드 할당 단위(프로젝트/네임스페이스 등) ↔ service (§4.1) |
| ④ | 소비 관계 | "A → B(플랫폼)의 모델 M" — 사내 플랫폼 소비 시 (§4.3) |
| ⑤ | 서비스 계정 매핑 | (플랫폼만) 서비스 계정 ↔ 소비 서비스 — 자기신고로 대체 가능 (§6.4) |
| ⑥ | `/metrics` URL | (케이스 A~C만) 스크랩 대상 URL + 엔진 종류 (§5.2) |

**항목 구조 예시** (양식의 한 서비스 분):

```yaml
serviceGroup: claude
service: claude-cowork
owner: kim@company.com
gpuAllocationUnit: "k8s-ns:claude-cowork-prod"    # GPU 대시보드 할당 단위 매핑
engine: { type: vllm }                             # 버전은 자기신고로 수신
metricsUrl: "http://cowork-vllm.internal:8000/metrics"
models:
  - canonical: opus
    family: claude
    sizeClass: L                                   # S(~15B) | M(~40B) | L(40B+) — MoE는 활성 파라미터 기준
    aliases: ["anthropic/claude-opus", "opus-fp8"]
consumes: []            # 사내 플랫폼 소비 시: [{ platform: llm-gateway, model: llama3.3-70b }]
serviceAccounts: {}     # 플랫폼인 경우: 서비스 계정 ↔ 소비 서비스 매핑 (자기신고로 대체 가능)
```

**자동화 우선 원칙 — 사람 입력은 최후 수단.** 취합 항목 대부분은 사실 시스템이 이미 알고 있다:

| 항목 | 갱신 채널 |
|---|---|
| 엔진 종류·버전 | `/v1/metrics` `engine` **자기신고** (§6.4) — 수기 갱신 불필요 |
| 신규 모델 표기 | **데이터 유입 자동 감지** → "미등록" 격리·알림 → 담당자 확인 후 "기존 canonical에 alias 연결" 또는 "새 canonical 생성"을 취합본에 반영 (§3.1 폐루프) |
| 플랫폼 계정 ↔ 소비 서비스 | **플랫폼이 자기신고** — 키 발급 대장의 source of truth는 플랫폼이므로, 플랫폼의 `/v1/metrics` 응답에 `serviceAccounts` 매핑을 포함(선택, §6.4)하거나 취합본으로 제출 |
| user ↔ 조직 | 사내 조직도(HR) **연동** |
| service 표기, GPU 할당 매핑, 소비 관계 | **온보딩 1회 취합** + 변경 시 갱신 — 진짜로 사람만 아는 정보만 남는다 |

- **정합성 감시**: 자기신고·자동감지 값과 취합본이 어긋나면 알림 — 취합본 스테일을 자동 감지한다.
- 담당자 관점 요약: 온보딩 때 양식 한 번 채우고, 이후에는 새 모델 알림이 오면 분류만 회신. 엔진 버전은 신경 쓸 필요 없다.

**향후 — 대시보드 등록 화면 전환 검토.** 수기 취합은 규모가 커지면 한계가 있어, 등록 화면 전환을 검토한다. 방식 비교:

| 방식 | 평가 |
|---|---|
| **대시보드 등록 화면 (웹 폼 + DB)** | **전환 시 1순위.** 담당자 진입장벽 최소, 스키마 검증을 입력 시점에 강제, 수집기와 정본 공유, 변경 이력은 DB에 기록 |
| Git PR | 이력·리뷰는 좋으나 비개발 담당자에게 장벽, 저장소 권한 관리 부담 |
| Confluence | **정본으로는 부적합** — 기계가 읽기 어렵고(표 파싱 취약) 입력 검증이 불가하며 스테일이 방치된다. 단, 정본에서 **자동 생성하는 read-only 현황 페이지**로 쓰는 것은 좋다 (사람이 보는 뷰와 기계가 읽는 정본을 분리) |

**엔진 종류·버전이 필요한 이유**:

- §5.2의 케이스 분기와 Prometheus 메트릭명 매핑이 엔진 종류·버전에 의존한다 (vLLM/SGLang은 버전에 따라 메트릭 명칭이 다름).
- **엔진 업그레이드는 성능 변화의 주요 원인**이다. 버전 이력이 있어야 "지난주부터 ITL이 올라간 이유"를 추적할 수 있다.
- 같은 모델을 다른 엔진으로 서빙하는 팀 간 효율 비교(토큰/GPU-hour)가 가능해져 전사 최적화 인사이트가 된다.

## 4. 모델별 GPU Hour

### 4.1 비용 산출 기준과 수집 항목

**비용의 정본은 할당이다.** GPU는 서비스에 할당되는 순간부터 점유 비용이 발생하므로(가동 여부와 무관), 서비스별 일 비용은 다음으로 산출한다.

```
서비스 일 비용 = 할당 GPU-hours (GPU 대시보드) × 기종별 단가
할당 GPU-hours = 할당 GPU 수 × 24h (기종별)
```

`/v1/metrics`의 gpu 블록은 **이 할당 비용이 어떤 용도로 쓰였는지의 분해**다. 서비스는 service × model × gpuType × category 단위로 일별 `gpuCount`·`gpuHours`를 제공한다.

- **gpuHours** = GPU 개수 × 매핑·할당 시간 (모델에 GPU가 매핑·할당된 시간). 예: H100 4장 × 24시간 = 96.0
- **gpuCount** = 해당일 그 모델에 매핑된 GPU 수. 하루 중 증감이 있으면 **최대 수 기준** — 실제 총량은 gpuHours가 표현한다.
- **gpuType**: **단순 기종 표기** (예: `H100`, `A100`). 할당·단가와 대조하는 키이므로 필수.
- **category**: 용도 분류. 제공 대상은 아래 3개.

| category | 의미 | model 값 | 제공 주체 |
|---|---|---|---|
| `serving` | 프로덕션 서빙 | 실제 모델명 (`unknown` 금지) | 서비스 |
| `standby` | HA 대기 (failover용) | 실제 모델명 (`unknown` 금지) | 서비스 |
| `test` | 테스트·실험용 | 모델명 또는 `unknown` | 서비스 |
| (유휴) | 어느 용도에도 쓰이지 않은 잔여 | — | **제공하지 않음 — 중앙 산출** |

- **유휴는 서비스가 제공하지 않는다.** 중앙이 `유휴 = 할당 GPU-hours − Σ(제공된 serving+standby+test)`로 산출한다. 서비스가 인지하지 못한 미사용분까지 자동으로 잡히고, 제공 부담도 줄어든다.
- **정합성 검증**: ① 기종별로 Σ(제공 gpuHours) ≤ 할당 GPU-hours, ② 항목별로 gpuHours ≤ gpuCount × 24, ③ serving/standby의 model=`unknown` 금지. 위반 시 데이터 오류로 담당자 알림.
- **효율 지표(원/1M토큰, 토큰/GPU-hour)는 `serving`만으로 계산.** standby를 포함하면 HA를 갖춘 팀이 비효율로 보이는 왜곡이 생기므로 제외하고, standby 비용("HA의 가격")과 유휴율·활용률은 별도 지표로 노출한다.
- **GPU 대시보드 연동 요건**: GPU 대시보드의 할당 단위(프로젝트/네임스페이스 등)와 본 체계의 service 식별자 매핑을 취합본에 제출해야 한다. 할당 데이터가 없거나 매핑이 불가한 서비스는 폴백으로 제공 기반 비용(Σ제공 gpuHours × 단가)을 사용하되, 이 경우 유휴가 잡히지 않아 비용이 과소계상될 수 있음을 명시한다.

### 4.2 유효 기간(effective) 처리

- 모델 교체·증설 이력은 **daily 팩트에 내재**된다. 각 날짜의 응답이 그날 실제 돌아간 구성을 반영하므로 별도의 effective_from/to를 제공할 필요 없다.
- **GPU 단가표만 예외**: 중앙이 (gpuType, 시간당 단가, effective_from)으로 이력 관리한다. 단가 개정이 과거 비용을 소급 변경하지 않기 위함. 담당자와 무관한 중앙 내부 마스터.

### 4.3 사내 서비스 간 사용 — 서비스 A가 서비스 B(LLM API 플랫폼)를 쓰는 경우

사내 서비스가 자체 GPU 대신(또는 병행하여) 다른 사내 서비스의 LLM API를 호출하는 경우의 수집·집계·비용 귀속 규칙.

#### 4.3.1 원칙 세 가지

1. **GPU Hour는 돌리는 쪽만 제공한다 (단일 제공 원칙).** GPU 시간·비용 데이터의 정본은 항상 GPU를 운영하는 서비스(B)다. 소비 서비스(A)는 B 사용분에 대해 GPU를 일절 제공하지 않는다. 같은 GPU 시간이 두 곳에서 잡히는 이중 계상을 원천 차단하기 위함이다.
2. **소비자 식별은 공급자 책임.** B는 호출 주체를 서비스 단위로 구분할 수 있어야 한다. 방법은 소비 서비스별 API 키(서비스 계정) 발급이 표준이다.
3. **비용은 두 관점으로 본다.** 운영 관점(비용이 *발생한* 곳 = B)과 사용 관점(비용을 *유발한* 곳 = A). 대시보드는 둘 다 보여주되, 어느 관점으로 합산해도 전사 총액은 동일해야 한다.

#### 4.3.2 수집 — 누가 무엇을 제공하나

| 주체 | GPU (`/v1/metrics`) | 토큰 (기존 토큰 API) |
|---|---|---|
| **B (공급자)** | 자기 명의로 모델별 전량 제공 (§4.1 그대로) | 제공하되 **소비 주체를 구분**: 서비스 소비자의 호출은 해당 서비스 계정의 userId로 집계됨. **정본(비용 배부 근거)은 B의 제공분** |
| **A (소비자)** | B 사용분에 대해 **제공 없음** (자체 GPU가 있으면 그것만 §4.1대로) | B 사용분에 대해 **제공 생략 권고** (아래 참조) |

- **소비자 식별 매핑**: 기존 토큰 API 스펙을 바꾸지 않고, "B의 서비스 계정(userId) ↔ 소비 서비스(serviceGroup, service)" 매핑을 취합본에 제출하는 것으로 해결한다. 중앙이 B의 usage 데이터에서 서비스 계정 행을 골라 소비 서비스로 치환한다.
- **소비 관계 등록**: "A는 B의 모델 M을 소비한다"는 관계 자체를 취합본에 제출한다. 이것이 중복 제거와 배부 계산의 기준이 된다.
- **A의 토큰 제공에 관하여**: A가 최종 사용자별 분석을 위해 B 경유 사용량을 자체 토큰 API로도 제공할 수 있으나(B는 A를 하나의 호출자로만 보므로 A의 최종 사용자는 A만 안다), 이 경우 같은 토큰이 두 번 잡힌다. 규칙: **전사 합계·비용 배부는 항상 공급자(B) 제공분만 사용**하고, A의 제공분은 취합본의 소비 관계를 근거로 전사 집계에서 제외한다(A 내부의 사용자별 분석 용도로만 활용).

#### 4.3.3 비용 배부 규칙

- B의 **모델별 `serving` 비용**을 그 모델의 소비자별 토큰 비율로 배부한다. B 자체 트래픽(B의 직접 사용자)도 하나의 소비자로 취급한다.
- **배부 키: 가중 토큰 = inputTokens × 1 + outputTokens × 4.** input:output = 1:4 가중치는 GPU TCO측이 제안한 확정 비율로, prefill 대비 decode의 GPU 연산 비중을 반영한다. 소비자별 배부율 = 소비자 가중 토큰 ÷ 해당 모델 총 가중 토큰.
- B의 **standby / test / 유휴 비용은 배부하지 않는다.** 플랫폼 운영 비용으로 B에 귀속하고, 대시보드에 "플랫폼 오버헤드"로 표시한다. (소비자에게 배부하면 소비자가 통제할 수 없는 비용을 떠안게 되어 논쟁만 생긴다.)

**숫자 예시** — B가 `llama3-70b`를 serving 96 gpuHours(단가 6,500원 → 624,000원) + standby 24 gpuHours(156,000원) 운영, 당일 해당 모델의 가중 토큰(1:4) 비율이 A 40% / C 25% / B 직접 사용자 35%인 경우:

| 귀속처 | 배부 비용 | 근거 |
|---|---|---|
| A | 249,600원 | serving 624,000 × 40% |
| C | 156,000원 | serving 624,000 × 25% |
| B (직접 사용분) | 218,400원 | serving 624,000 × 35% |
| B (플랫폼 오버헤드) | 156,000원 | standby — 배부 제외 |
| **합계** | **780,000원** | = B의 총 운영 비용과 일치 (무손실 배부 검증) |

#### 4.3.4 대시보드 표시

- **소비 서비스(A) 상세**: `총 비용 = 직접 비용(자체 GPU) + 배부 비용(사내 플랫폼 사용)`. 두 항목을 구분 표시.
- **공급 서비스(B) 상세**: 총 운영 비용, 소비자별 배부 내역, 플랫폼 오버헤드(미배부분).
- 전사 합계는 운영 관점 합 = 사용 관점 합 (검증 지표로 활용).

#### 4.3.5 성능 메트릭의 한계

B의 추론 엔진 메트릭(TTFT/ITL)에는 호출자 구분이 없으므로, 성능은 **B × 모델 단위**로만 집계된다. A별 체감 성능이 필요하면 A가 자기 게이트웨이에서 자체 측정하여 경로 (a)로 제공한다(§5.2 케이스 E와 동일한 방식 — 측정 위치가 다르므로 엔진 기준 수치와 단순 비교하지 않는다).

#### 4.3.6 하이브리드·다단계

- **하이브리드** (A가 자체 GPU도 운영하면서 B도 사용): 자체분은 §4.1대로 제공하고, B 사용분은 배부로 귀속된다. 대시보드에서 합산.
- **다단계 체인** (B가 다시 C를 소비): 같은 규칙을 재귀 적용하면 풀리지만 집계 복잡도가 커지므로, 1단계에서는 소비 체인을 1홉으로 제한할 것을 권장한다.

#### 4.3.7 플랫폼 직접 사용자(개인)의 귀속

플랫폼 API를 서비스가 아닌 **개인(직접 사용자)**이 호출하는 경우의 처리.

- **결정: user 레벨로 분해하여 귀속한다.** "직접 사용자 사용량"으로 뭉뚱그리지 않는다. 근거: ① 기존 토큰 API가 이미 date × userId × model 단위 데이터를 갖고 있으므로 **추가 수집 없이 배부 계산만 user 단위로 내리면 된다.** ② 뭉뚱그리면 "직접 사용" 덩어리가 커질수록 아무도 책임지지 않는 비용 사각지대가 된다.
- **롱테일 대응 — 귀속과 표시를 분리한다.** 귀속(계산)의 정본은 user 단위로 유지하되, 대시보드 기본 표시는 **user → 조직(부서/팀) 매핑으로 rollup**하여 상위 N개 조직 + "기타"로 보여준다. user 단위는 드릴다운으로만 제공한다. 개인별 비용의 전면 노출은 민감할 수 있으므로 기본 화면은 조직 단위를 권장한다.
- user → 조직 매핑은 사내 조직도(HR) 데이터와 연동하거나 취합본으로 관리한다. 매핑되지 않는 userId(퇴사자·시스템 계정 등)는 "미분류"로 표시하고 주기적으로 점검한다.
- 배부 계산에서 직접 사용자는 §4.3.3의 소비자 집합에 user 단위로 포함되며, 서비스 소비자와 동일한 가중 토큰(1:4) 규칙을 적용한다.

## 5. 서비스 메트릭

### 5.1 지표 정의

| 지표 | 정의 | 단위 | 수집 형태 |
|---|---|---|---|
| **TTFT** (Time To First Token) | 요청 수신 → 첫 토큰 생성까지 | ms | p50 / p90 / p99 |
| **ITL** (Inter-Token Latency) | 첫 토큰 이후 토큰 간 간격 | ms | p50 / p90 / p99 |
| **Output TPS** | 요청당 초당 생성 토큰 수 | tokens/s | avg / p50 |

- 평균만 받지 않고 percentile을 받는 이유: 평균은 소수의 느린 요청을 가리므로, 대다수 경험(p50)과 최악 경험(p99)을 구분해야 한다.
- requestTPS(RPS)는 받지 않는다 — 일평균은 기존 토큰 API의 requests에서 파생 가능. 피크 RPS는 용량 계획이 목적이 되는 시점에 2단계로 추가.
- **측정 위치 기준: 추론 엔진.** 게이트웨이 대기·네트워크 시간이 빠진 값이므로 사용자 체감보다 낙관적일 수 있으나, 전 서비스가 같은 위치에서 측정하므로 서비스 간 비교는 성립한다.

### 5.2 수집 경로 — 케이스별 가이드

담당자는 자기 서비스가 아래 어느 케이스인지 확인하고 해당 경로를 따르면 된다.

#### 케이스 A. vLLM 사용 → 경로 (b) 중앙 스크랩. **구현 작업 없음**

vLLM은 Prometheus 형식 `/metrics` 엔드포인트를 기본 노출하며, 필요한 지표가 이미 들어 있다.

| 대시보드 지표 | vLLM 메트릭 (히스토그램) |
|---|---|
| TTFT | `vllm:time_to_first_token_seconds` |
| ITL | `vllm:time_per_output_token_seconds` |
| (참고) E2E | `vllm:e2e_request_latency_seconds` |
| (참고) 생성 토큰 | `vllm:generation_tokens_total` (카운터) |

- 담당자가 할 일: **`/metrics` URL을 취합본에 제출하고 중앙 Prometheus에서 접근 가능하도록 네트워크만 개방.** GET `/v1/metrics`의 `serving` 블록은 비워도 된다. `--served-model-name`은 canonical 모델명으로 설정할 것을 권장한다(§3.1).
- 중앙이 하는 일: 1분 간격 스크랩 → daily 집계 시 그날 증가분(increase)으로 일별 히스토그램 구성 → p50/p90/p99 계산.
- 이 경로의 장점: ① 레플리카가 여러 대여도 히스토그램 버킷은 합산 가능하므로 집계가 정확하다. ② 버킷을 보존하므로 주간·월간 p99 재계산도 가능하다. (집계된 percentile 숫자는 재집계 불가 — 경로 (a)의 한계)
- 주의: 스크랩 시작 이후 데이터만 존재한다(과거 소급 불가). 엔진 재시작 시 카운터가 리셋되지만 Prometheus의 increase 계산이 이를 처리한다.

#### 케이스 B. SGLang 사용 → 경로 (b) 중앙 스크랩. 구현 작업 없음

SGLang도 Prometheus `/metrics`를 노출한다 (`--enable-metrics` 필요할 수 있음, 버전에 따라 메트릭명 상이 — 제출 시 중앙에서 매핑 확인). TTFT·토큰당 생성시간 히스토그램이 제공되므로 케이스 A와 동일하게 URL 제출 + 네트워크 개방만 하면 된다.

#### 케이스 C. 기타 Prometheus 지원 엔진 (TGI, TensorRT-LLM/Triton 등) → 경로 (b) 우선 검토

`/metrics`를 노출하는 엔진이면 케이스 A/B와 동일 경로가 가능하다. 메트릭 명칭이 엔진마다 다르므로 제출 시 중앙과 함께 "어느 메트릭이 TTFT/ITL에 해당하는지" 매핑표를 확정한다. 히스토그램이 아닌 summary/gauge만 제공하는 엔진은 케이스 D로 전환.

#### 케이스 D. 자체 구현 서빙 (FastAPI 등 직접 구현, 비표준 엔진) → 경로 (a) 자체 집계 제공

엔진이 메트릭을 내보내지 않으므로 서비스가 직접 측정·집계한다.

- 측정 방법 예시: 스트리밍 응답 코드에서 `요청 수신 시각`, `첫 청크 전송 시각`, `각 청크 전송 시각`을 로깅 → TTFT = 첫 청크 − 수신, ITL = 청크 간 간격, Output TPS = 출력 토큰 수 ÷ (마지막 청크 − 첫 청크).
- 하루치 로그에서 p50/p90/p99를 계산해 GET `/v1/metrics` 응답의 `serving` 블록에 채운다.
- 한계: 집계된 percentile 숫자는 재집계·레플리카 합산이 부정확하다. 레플리카가 여러 대면 전체 로그를 모아 한 번에 percentile을 계산할 것 (레플리카별 p99의 평균 ≠ 전체 p99).

#### 케이스 E. 외부 API 연동 서비스 (사내 GPU 없이 외부 상용 API 호출) → 경로 (a), gpu는 빈 배열

- GPU 비용이 없으므로 `gpu: []`. (외부 API 비용은 토큰 단가 기반으로 중앙이 별도 산출 — 기존 토큰 API 데이터로 충분)
- 서비스 메트릭이 필요하면 게이트웨이에서 측정한다. 측정 위치가 "엔진"이 아닌 "게이트웨이"이므로, 제출 시 측정 위치를 명시한다 (타 서비스와 단순 비교 시 주의 필요).

#### 케이스 F. 비스트리밍 서비스 (응답을 한 번에 반환) → 경로 (a), TTFT/ITL 해당 없음

- 첫 토큰 = 마지막 토큰이므로 TTFT/ITL 개념이 없다. `serving` 블록을 생략하거나, 2단계에서 E2E 지연시간 필드 추가 시 그것만 제공한다.

**요약표**

| 케이스 | 경로 | 담당자 작업 | serving 블록 |
|---|---|---|---|
| A. vLLM | (b) 중앙 스크랩 | /metrics URL 제출 + 네트워크 개방 | 생략 |
| B. SGLang | (b) 중앙 스크랩 | 상동 (+메트릭명 매핑 확인) | 생략 |
| C. 기타 Prometheus 엔진 | (b) 우선 | 상동 (+매핑표 확정) | 생략 |
| D. 자체 구현 | (a) 자체 집계 | 측정 로깅 + daily 집계 + GET 제공 | 채움 |
| E. 외부 API 연동 | (a) | 게이트웨이 측정 (선택) | 선택 |
| F. 비스트리밍 | (a) | — | 생략 |

## 6. API 계약: GET /v1/metrics

기존 token-usage-api-spec의 규칙을 그대로 상속한다.

### 6.1 요청

```
GET https://{service-host}/v1/metrics?date=YYYY-MM-DD
```

- `date`: KST 기준 하루 (기본적으로 어제). 인증 없음(사내망 전제).

### 6.2 응답 규칙 (기존 스펙 상속)

| 상황 | 응답 |
|---|---|
| 확정된 데이터 있음 | `200` + 본문 |
| 사용량·가동이 실제 0 | `200` + 빈 배열 (`gpu: []`) |
| 아직 집계 전 (미확정) | `409` — 빈 200 금지. "0"과 "아직 없음"을 구분 |
| 당일/미래 date | `400` |
| 보존 기간 초과 | `404` |

- 응답에 집계 산출 시각 `generatedAt` (KST, `+09:00`) 포함.
- 같은 date 재호출 시 동일 결과 반환 (중앙이 재수집해도 안전 — 정정 시 서비스가 재집계 후 중앙에 재수집 요청).

### 6.3 응답 스키마·예시

**예시 1 — vLLM 팀 (케이스 A): serving 생략**

```json
{
  "date": "2026-08-18",
  "serviceGroup": "claude",
  "service": "claude-cowork",
  "generatedAt": "2026-08-19T01:30:00+09:00",
  "engine": { "type": "vllm", "version": "0.8.4" },
  "gpu": [
    { "model": "opus", "gpuType": "H100", "gpuCount": 4, "gpuHours": 96.0, "category": "serving" },
    { "model": "opus", "gpuType": "H100", "gpuCount": 1, "gpuHours": 24.0, "category": "standby" }
  ],
  "serving": []
}
```

**예시 2 — 자체 구현 팀 (케이스 D): serving 포함**

```json
{
  "date": "2026-08-18",
  "serviceGroup": "search",
  "service": "doc-summary",
  "generatedAt": "2026-08-19T01:10:00+09:00",
```

**예시 3 — 외부 API 연동 서비스 (케이스 E): gpu 빈 배열**

```json
  "serviceGroup": "hr",
```

### 6.4 필드 정의

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `date` | string (YYYY-MM-DD) | O | KST 기준 집계 대상일 |
| `serviceGroup` / `service` | string | O | 취합본 공식 표기와 일치 |
| `generatedAt` | string (ISO 8601, +09:00) | O | 집계 산출 시각 |
| `engine` | object {type, version?} | X (권장) | 엔진 자기신고 (§3.2). 예: `{"type":"vllm","version":"0.8.4"}`. 취합본 값과 불일치 시 중앙이 알림 |
| `serviceAccounts` | object | X | 플랫폼만: 서비스 계정 ↔ 소비 서비스 매핑 자기신고 (§3.2). 예: `{"svc-key-a1": "chat-assistant"}` |
| `gpu[]` | array | O (빈 배열 허용) | |
| `gpu[].model` | string | O | 공식 표기. `"unknown"`은 category=test에서만 허용 (§4.1) |
| `gpu[].gpuType` | string | O | 단순 기종 표기 (예: `H100`, `A100`) — 단가표 키 |
| `gpu[].gpuCount` | number | O | 해당일 매핑된 GPU 수 (하루 중 증감 시 최대 수 기준) |
| `gpu[].gpuHours` | number | O | GPU 수 × 매핑·할당 시간 (≤ gpuCount × 24) |
| `gpu[].category` | enum | O | `serving` \| `standby` \| `test` — 유휴는 제공하지 않음 (중앙 산출, §4.1) |
| `serving[]` | array | X (생략/빈 배열 허용) | 경로 (a) 팀만 |
| `serving[].model` | string | O | |
| `serving[].ttftMs` | object {p50,p90,p99} | X | ms |
| `serving[].itlMs` | object {p50,p90,p99} | X | ms |
| `serving[].outputTps` | object {avg,p50} | X | tokens/s |

- 토큰량·requests 필드는 **없다** — 기존 토큰 API 담당 (이중 소스 금지).

## 7. 운영 규칙

- 중앙 수집기가 **02:00(KST)부터** 전일 데이터 호출 시작. `409`(집계 전)이면 1시간 간격 재시도, **09:00까지 미확정이면 담당자 알림.**
- 최근 7일까지 재수집(backfill) 가능 — 정정이 필요하면 서비스가 재집계 후 중앙에 재수집을 요청한다.
- 단위는 필드명에 명시 (`Ms`, `gpuHours`, `Tps`) — 단위 착오 방지.
- Prometheus 스크랩 대상(케이스 A~C)은 (service, /metrics URL, 엔진 종류)을 취합본에 제출한다(§3.2 — 엔진 버전은 자기신고로 수신). 엔진 메트릭에는 service 라벨이 없으므로 스크랩 설정에서 중앙이 라벨을 부여하고, 모델 라벨은 §3.1의 alias 사전으로 정규화한다.

## 8. 대시보드 산출 지표 (참고: 중앙 계산)

JOIN 키: (date, serviceGroup, service, model) — 기존 토큰 API × 신규 metrics API × 단가표

| 지표 | 계산 | 데이터 출처 |
|---|---|---|
| 일별 비용 (직접) | 할당 GPU-hours × 해당일 단가 (§4.1) | GPU 대시보드 + 단가표 |
| 활용률 | serving gpuHours ÷ 할당 GPU-hours | metrics API + GPU 대시보드 |
| 배부 비용 (사내 플랫폼 사용) | 공급자의 모델별 serving 비용 × 소비자 토큰 비율 (§4.3.3) | + 기존 토큰 API + 소비 관계 취합본 |
| 원/1M 출력토큰 | serving 비용 ÷ (outputTokens ÷ 1M) | + 기존 토큰 API |
| 토큰/GPU-hour | outputTokens ÷ serving gpuHours | 〃 |
| 유휴율 | (할당 GPU-hours − Σ제공 gpuHours) ÷ 할당 GPU-hours | metrics API + GPU 대시보드 |
| standby 비용 | standby gpuHours × 단가 | metrics API |
| TTFT/ITL p50·p99 추이 | 일별 시계열 | Prometheus 또는 serving 블록 |
| 모델 채택도 | canonical별 사용 서비스 수·직접 사용자 수, 신규 채택·이탈 | 기존 토큰 API + 소비 관계 취합본 |
| 모델 토큰 점유율·추세 | canonical별 가중 토큰 점유율과 그 증감 | 기존 토큰 API |

- 효율 지표의 분모·분자는 category=`serving`만 사용.
- 성능 지표는 서비스·모델 단위로만 표시 (서비스 간 합산 평균은 무의미).

**라지모델 편향 방지 — 표시 원칙 (v2.1)**

현재 지표 체계(원/1M토큰, TTFT/ITL, GPU Hour)는 전 축이 라지모델에 불리해서, 그대로 랭킹하면 대시보드가 "다운사이징 압력 장치"가 되는 구조적 편향이 있다. 비용·배부 숫자는 사실대로 두고, **비교·표시 계층**에서 다음 원칙으로 교정한다:

- **효율 랭킹은 체급(sizeClass) 내에서만.** 원/1M토큰·토큰/GPU-hour 랭킹은 S/M/L 각 리그 안에서만 표시하고, 체급 간 줄 세우기 화면은 만들지 않는다. (8B와 70B를 한 표에 놓고 비교하지 않는다)
- **라지모델의 가치는 채택도로 표현한다.** 대안이 있는데도 많은 서비스·사용자가 찾는다는 사실(revealed preference)을 가치의 증거로 강조 — 모델 현황판(3단 드릴다운, §3.1)에 sizeClass·채택도(사용 서비스 수·토큰 점유율 추세) 컬럼을 병기한다.
- **서비스 간 효율 비교는 같은 canonical 내에서만.** 같은 모델을 쓰는 팀 간 격차는 순수 운영 노하우 비교라 체급과 무관하게 공정하다.
- 품질 점수 축(비용×품질 프런티어)은 현시점 미도입 — 2단계 검토 (§9).

**서비스 상세 표준 뷰** — "할당받은 GPU를 어떻게 쓰고 있는가"에 한 화면으로 답하는 표준 흐름:

```
할당 (GPU 대시보드: 기종 × 장수 × 24h)
  → 용도 분해 (serving / standby / test / 유휴) + 활용률
    → 성능 (모델별 TTFT·ITL p50/p99)
      → 산출 (토큰량 — 기존 토큰 API)
        → 비용·효율 (일 비용, 원/1M토큰, 토큰/GPU-hour)
```

모든 서비스 상세 화면을 이 순서로 통일하면, "어떤 GPU를 받아 → 서빙에 얼마나 쓰고 → 성능은 어떻고 → 비용·효율은 어떤가"가 위에서 아래로 읽힌다.

## 9. 일정과 단계별 로드맵

**일정**

- **~9/18**: `/v1/metrics` API 구축 완료 및 대시보드 연동
- **그 전까지**: 관리 정보·수치를 수기(엑셀)로 취합 (§3.2)

**1단계 (비용 대시보드 성립)**
1. (serviceGroup, service, model) 공식 표기 목록 확정 — 취합본 v1 (엑셀, §3.2)
2. GPU 대시보드 연동: 할당 단위 ↔ service 매핑 제출, 일별 할당 GPU-hours 확보 (§4.1)
3. 소비 관계 제출: "A → B의 모델 M" 관계 + 플랫폼(B)의 서비스 계정↔소비 서비스 매핑 (§4.3.2)
4. 각 서비스: GET `/v1/metrics` 구현 (**gpu 블록만으로 충분**)
5. vLLM/SGLang 팀: /metrics URL 제출 + 네트워크 개방
6. 중앙: 수집 크론 확장, 단가표 구축, 할당 기준 비용·활용률·유휴율 대시보드 + 배부 비용 표시(showback — 직접 사용자는 user 단위 귀속, §4.3.7)

**2단계 (성능·고도화)**
- 경로 (a) 팀의 serving 블록 제공
- 배부 비용의 실제 정산(chargeback) 여부 협의, user → 조직 rollup 뷰 (§4.3.7)
- E2E 지연(비스트리밍), 피크 지표(peakHourRequests 등), 그룹 공통 GPU의 하위 배부, 소비 체인 다단계 지원
- 품질 축 도입 검토: canonical별 품질 점수(사내 평가셋 또는 공개 지수 인용 — suite 버전 명시) + 비용×품질 프런티어 뷰. 모델 다운사이징 의사결정은 프록시 지표가 아닌 델타 실험(작은 모델로 교체 시 재질문율·채택률 변화 측정)으로 판정
- 관리 정보 취합의 등록 화면 전환 검토 (§3.2 "향후")
