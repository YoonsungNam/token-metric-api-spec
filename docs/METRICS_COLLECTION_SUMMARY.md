# AI 서비스 비용·성능 메트릭 수집 체계 — 담당자 요약 (미팅용)

> **대상**: 각 AI 서비스 담당자 · **성격**: 미팅 참고용 축약본 — 구현 규칙·필드 정의·예시 전문은 [구현 스펙](METRICS_COLLECTION_SPEC.md) 참조
> **역할 표기**: **담당자** = AI 서비스 담당자 (이 문서의 독자) / **운영자** = 토큰 대시보드 개발·운영팀

---

## 1. 무엇을, 왜 하나

지금은 기존 토큰 API로 **토큰 사용량·요청 수**만 daily 수집 중. 여기에 두 가지를 추가해 **비용·효율·성능을 한 화면**에서 본다.

| 추가 수집 항목 | 목적 |
|---|---|
| **모델별 GPU Hour** (모델에 GPU가 매핑·할당된 시간) | 할당 비용의 용도 분해와 효율 산출 (비용 자체는 GPU 대시보드의 할당 기준) |
| **성능 메트릭** (TTFT·ITL·Output TPS·E2E) | 원/1M토큰 산출 · 비용 변화 원인 분해 · 비용 조정 안전장치 · 공유 모델 배부 근거 |

**설계 원칙**: ① 이중 소스 금지(토큰량·requests는 다시 안 받음) ② 기존 토큰 API 계약 상속(pull·식별자·응답 규칙) ③ 담당자 부담 최소 (신규 구현은 GET 1개 — 성능 집계는 엔진 히스토그램 활용 가능)

## 2. 해야 할 일 (한눈에)

| 누가 | 무엇을 | 언제까지 |
|---|---|---|
| **모든 서비스** | ① 메타데이터 시트(엑셀) 제출 ② GET `/v1/metrics` 구현 — gpu 블록 | 시트: 온보딩 시 / API: **~9/18** |
| GPU 서빙 팀 전체 (케이스 A~D·F) | ③ serving 블록 자체 집계 제공 (A~C는 엔진 히스토그램 활용 가능) | ~9/18 |
| vLLM/SGLang 등 Prometheus 엔진 팀 | ③′ **검증용** `/metrics` URL(VIP) 제출 + 방화벽 개방 — 운영자가 자기신고 값을 교차 검증 | 온보딩 시 |
| 사외 AI 모델 API 팀 | ③ serving 블록 자체 집계 — **선택** | 원할 때 |

- 방향은 **pull**: 운영자가 매일 새벽 호출, 크론·재시도·장애 감지는 운영자 책임. 서비스는 상태 없는 GET만.
- **~9/18 전까지는 수치를 수기(엑셀)로 취합.**

## 3. 전제 — "기존 토큰 API"란

각 서비스가 일별 토큰·요청 수를 제공하는 사내 표준 GET `/v1/usage` ([token-usage-api-spec](https://github.com/YoonsungNam/token-usage-api-spec)). `/v1/metrics`는 그 자매 API. **아직 `/v1/usage`가 없는 신규 서비스**는 시트에서 표기를 먼저 확정하고 두 API를 같은 표기로 함께 온보딩하면 된다.

## 4. 식별자와 모델 표기

- `serviceGroup > service > model` — **기존 토큰 API와 같은 문자열** (불일치 시 JOIN 실패)
- `model`은 canonical 표기. `"unknown"`은 **test 카테고리에서만** 허용
- **canonical/alias**: 공식 이름 하나(canonical)에 실데이터의 모든 표기(HF 경로·served-model-name·기존 토큰 API 표기·사외 API 날짜 버전)를 alias로 연결 — **기존 표기는 바꿀 필요 없음**, 운영자가 정규화
- 나눔/합침 3문항: 같은 웨이트? 순정? 같은 정밀도? — 하나라도 "아니오"면 별도 canonical. **사내 파인튜닝은 반드시 `-ft-{용도}` 분리. 애매하면 나눈다**
- **모델 크기는 원시 값으로**: `paramsB`(총 파라미터, B 단위) + MoE는 `activeParamsB`(활성) 병기 — 체급(효율 리그) 분류는 운영자가 파생하며 경계는 추후 조정 가능
- 미등록 표기가 유입되면 운영자가 후보와 함께 알림 → "기존 canonical의 alias / 새 모델" 택일 회신이면 끝 (폐루프)

## 5. 메타데이터 시트 (엑셀)

서비스 기준 정보의 정본. 온보딩 시 1회 작성, 이후는 **알림 기반 갱신** (기억할 필요 없음 — 미등록 모델·엔진 교체·검증 위반·미매핑 unit을 운영자가 감지해 알림).

| # | 항목 | 요점 |
|---|---|---|
| [1] | 서비스 표기 | serviceGroup·service·담당자(owner — 알림 수신 주소) |
| [2] | 모델 표기 | **쓰는 모델 전부** (자체 서빙 + 사내 플랫폼 경유 + 사외 AI 모델 API). canonical 정의(alias·family·paramsB)는 서빙 주체만, 플랫폼 경유 모델은 이름만 참조 |
| [3] | GPU 할당 매핑 (`gpuDashboardUnits`) | GPU 대시보드 할당 unit 목록 — 항목당 `infraType`·`workgroup`·`unit`(선택). **unit 비우면 워크그룹 전체**(하위 unit 자동 포함, 권장), 공유 워크그룹만 unit 지정 |
| [4] | 소비 관계 (`consumes`) | models 중 외부 조달 모델의 출처: `{model, provider, type: internal/external}` — **없는 모델 = 자체 서빙** |
| [5] | `/metrics` URL | (케이스 A~C만) **검증용** 스크랩 VIP + 엔진 종류 — 버전은 API 자기신고 |

## 6. gpu 블록 — 모델별 GPU Hour

model × gpuType × category 단위 행으로 일별 제공:

- **`gpuHours`** = 장수 × 매핑·할당 시간(적분) — **비용의 유일한 근거**: 비용 = gpuHours × 단가(**원/GPU·hour**)
- **`gpuCount`** = 그날 최대 장수 — "몇 장 점유" 표시·검증용, **비용 계산 미사용**
- **`gpuType`** = 단순 기종 표기 (H100, A100)
- **category** = `serving` / `standby`(HA 대기) / `test`(실험, unknown 허용) — 구분 이유: standby 섞으면 HA 팀 효율 왜곡, test 안 나누면 실험분이 유휴 오탐. 해당 용도 없으면 serving 행만
- **유휴는 제공하지 않음** — 운영자가 `할당(고정 쿼터) − Σ제공`으로 산출
- 하루 중 변동: 장수 증감은 gpuHours에 반영, **기종 변경·주간/야간 모델은 행 분리**. 시간대별 프로파일은 안 받음(단가가 일 단위라 비용 정확). 오토스케일링 도입돼도 계약 불변
- 검증(위반 시 알림): Σ제공 ≤ 할당 / gpuHours ≤ gpuCount×24 / serving·standby에 unknown 금지

## 7. 사내 플랫폼을 쓰거나 제공하는 경우

- **GPU Hour는 돌리는 쪽만 제공** (단일 제공 원칙) — 소비자는 플랫폼 사용분의 GPU·토큰을 **제공하지 않음** (이중 계상 차단), 시트에 consumes만 등록
- **소비자 식별은 공급자 책임** — API 키 **발급 시 소비 서비스의 `service` 표기를 받아 기록**하고, 사용량 제공 시 그 표기로 소비자 호출분을 구분 (키 매핑 제출 없음)
- 배부: 공급자의 모델별 serving 비용을 가중 토큰(input×1+output×4) 비율로 소비자에 귀속. standby·test·유휴는 배부하지 않음(플랫폼 오버헤드)

## 8. 성능 메트릭 — 내 케이스 찾기

**자체 GPU 서빙 팀 전체(케이스 A~D·F)가 serving 블록을 작성한다** — 사외 API 전용(E)만 선택. Prometheus 엔진 팀은 추가로 검증용 `/metrics`를 개방한다. 자체 GPU 없이 사내 플랫폼만 소비하는 서비스는 `gpu: []`·`serving: []`.

| 케이스 | 담당자 작업 | serving 블록 |
|---|---|---|
| A. vLLM | serving 집계(엔진 히스토그램 활용) + 검증용 URL 개방 | 채움 |
| B. SGLang | 상동 (`--enable-metrics` 필요할 수 있음) | 채움 |
| C. 기타 Prometheus 엔진 | 상동 + 메트릭명 매핑 확정 | 채움 |
| D. 자체 구현 서빙 | 시각 로깅 → daily 집계 → GET 제공 | 채움 |
| E. 사외 AI 모델 API 연동 | `gpu: []`, 원하면 게이트웨이 측정 | 선택 |
| F. 비스트리밍 | `e2eMs`(표준)·`custom[]`(선택)으로 작성 | **채움** |

- 지표: **TTFT·ITL** 각 p50/p90/p95/p99, **Output TPS** p50만(avg·상위 percentile 없음), **E2E**(비스트리밍 필수), **custom[]**(구조 고정 자유 지표 — 해당 서비스 화면에 표시, 서비스 간 비교·SLO 불가)
- **성능의 정본은 서비스×모델 단위** — 모델 혼합값은 트래픽 비중에 좌우되므로 참고용만
- 운영자는 개방된 엔진 `/metrics`를 스크랩해 자기신고 값을 **교차 검증** — 집계 실수(레플리카 합산 오류 등)를 알림으로 잡음
- 레플리카 로그·버킷은 모아서 한 번에 percentile — 레플리카별 p99 평균 ≠ 전체 p99

## 9. API 계약 요점 — GET /v1/metrics?date=YYYY-MM-DD

| 상황 | 응답 |
|---|---|
| 확정 데이터 있음 / 실제 0 | `200` (+본문 / `gpu: []`) |
| 집계 전(미확정) | **`409` — 빈 200 금지** ("0"과 "아직 없음" 구분) |
| 당일·미래 / 보존 초과 | `400` / `404` |

- KST 기준, 사내망·인증 없음. 같은 date 재호출 = 동일 결과. `engine` 자기신고 권장(버전 수기 갱신 불필요)

## 10. 운영 규칙

- 운영자가 **02:00(KST)부터** 전일 호출, 409면 1시간 간격 재시도, **09:00까지 미확정 시 담당자 알림** → 02:00 이전 확정 필수
- 최근 **14일 backfill** — 정정 시 재집계 후 운영자에게 재수집 요청

## 11. 이걸 하면 보게 되는 것 (운영자 산출 — 참고)

일 비용(할당 기준) · 활용률 · 유휴율 · 배부 비용 · **원/1M토큰** · 토큰/GPU-hour · standby 비용 · TTFT/ITL 추이 · **모델 채택도**(사용 서비스·사용자 수, 토큰 점유율 추세)
→ 서비스 상세: `할당 → 용도 분해 → 성능 → 토큰 산출 → 비용·효율` 표준 뷰 (효율은 serving만, 성능은 모델 단위)
→ **효율 랭킹은 체급(파라미터 기반 리그) 내에서만** — 라지모델의 가치는 채택도로 강조. 품질 점수 축은 2단계 검토
