# AI 서비스 비용·메트릭 수집 체계 — 담당자 요약 (미팅용)

> **대상**: 각 AI 서비스 담당자 · **성격**: 미팅 참고용 축약본 (상세 규칙·예시는 정의서 본문 참조)

---

## 1. 무엇을, 왜 하나

지금은 기존 토큰 API로 **토큰 사용량·요청 수**만 daily 수집 중. 여기에 두 가지를 추가해 **비용·효율·성능을 한 화면**에서 본다.

| 추가 수집 항목 | 목적 |
|---|---|
| **모델별 GPU Hour** (모델에 GPU가 매핑·할당된 시간) | 할당 비용의 용도 분해와 효율 산출 (비용 자체는 GPU 대시보드의 할당 기준) |
| **성능 메트릭** (TTFT·ITL·Output TPS) | 원/1M토큰 산출 · 비용 변화 원인 분해(트래픽↑ vs 효율↓) · 비용 조정 안전장치 · 공유 모델 배부 근거 |

**설계 원칙 3가지**

1. **이중 소스 금지** — 기존 토큰 API가 주는 값(토큰량·requests·파생값)은 다시 받지 않는다
2. **기존 계약 상속** — pull 방식·식별자·응답 규칙 동일 (새로 배울 것 최소화)
3. **담당자 부담 최소** — 신규 구현은 서비스당 GET 1개. vLLM/SGLang 팀은 성능 메트릭 구현 자체가 불필요

## 2. 전체 구조 — 방향은 pull

중앙 수집기가 매일 새벽 각 서비스를 호출. **크론·재시도·장애 감지는 전부 중앙 책임**, 서비스는 상태 없는 GET만 제공.

```
중앙 수집기 (매일 새벽)
 ├─ (기존) GET /v1/usage?date=어제      ← 토큰·requests
 ├─ (신규) GET /v1/metrics?date=어제    ← GPU Hour (+비표준 엔진의 성능 메트릭)
 └─ (신규) 중앙 Prometheus가 vLLM/SGLang /metrics 상시 스크랩 → daily percentile 집계
```

**담당자가 하는 일 전부**: ① `/v1/metrics` GET 1개 구현 ② (vLLM/SGLang) `/metrics` URL 제출 + 네트워크 개방. 끝.

## 3. 용어 통일

| 용어 | 뜻 |
|---|---|
| 추론 엔진 | vLLM·SGLang 등 모델 실행 SW — 성능 메트릭의 기본 측정 위치 |
| 게이트웨이 | 요청을 엔진·외부/사내 API로 전달하는 자체 서버 계층 — 엔진 측정 불가 시 대체 측정 위치 |
| 플랫폼 / 소비 서비스 / 직접 사용자 | 사내 GPU로 API 제공하는 공급자 / 그 API를 쓰는 사내 서비스 / 개인 자격 호출자 |
| 외부 API 연동 서비스 | 사내 GPU 없이 외부 상용 API 호출 (구 "API 프록시" — **"프록시" 표기 사용 금지**) |
| **할당** vs **가동** | 서비스에 배정된 GPU(=**비용 발생 기준**) vs **모델에 GPU가 매핑되어 할당된 시간**(=`/v1/metrics`로 제공) |
| 배부 | 플랫폼 비용을 사용 비율로 소비자에 귀속 — showback(표시)과 chargeback(정산) 구분 |
| canonical vs alias | 공식 모델명 vs 그 외 모든 표기(HF 경로·체크포인트명·날짜 버전 등) |

## 4. 식별자 — 기존 토큰 API와 완전 동일

- 구조: `serviceGroup > service > model`, **수집 단위는 service** (serviceGroup은 합산 뷰)
- 기존 토큰 API와 **같은 문자열** 필수 — `claude` vs `Claude` 불일치 시 JOIN 실패
- 하위 서비스에 못 넣는 그룹 공통 GPU는 별도 service(예: `claude-shared`)로 등록
- `model` 필수 — `"unknown"`은 **test 카테고리에서만 허용** (serving/standby에서는 금지, 위반 시 데이터 오류 알림)

## 5. 모델명 규칙 (canonical id)

한 줄 원칙: **"다르게 불리는 같은 것은 합치고, 같게 불리는 다른 것은 나눈다."**

**판단 3문항** — 모두 "예"면 합침(alias 연결), 하나라도 "아니오"면 별도 canonical:
① 웨이트가 같은가 ② 파인튜닝 없는 순정인가 ③ 정밀도·양자화가 같은가

- **애매하면 나눈다** — 나눈 것은 나중에 합쳐 볼 수 있지만, 합쳐 쌓인 데이터는 분해 불가
- 사내 파인튜닝은 반드시 `-ft-{용도}` 접미 — 순정과 같은 id 사용 금지
- 양자화 변형은 분리(`-awq`, `-fp8`) / 외부 API 날짜 버전은 합침(`gpt-4o-2024-11-20` → `gpt-4o`)
- 표기 규칙: 소문자·하이픈, `{패밀리}{버전}-{크기}[-{변형}]`
- **기존 표기는 바꿀 필요 없음** — alias로 흡수. 미등록 표기가 데이터에 유입되면 "미등록"으로 격리 → 담당자 확인 후 canonical/alias로 분류·반영
- vLLM/SGLang: `--served-model-name`을 canonical로 설정하면 정규화 자체가 불필요
- 현황판은 **family → canonical → service 3단 드릴다운** — 전사 총량과 "누가 쓰는지"를 함께 봄
- **파라미터 수(paramsB) 기재**: 총 파라미터(B 단위), MoE는 활성(activeParamsB) 병기 — 체급(효율 리그) 분류는 운영자가 파생(경계 추후 조정 가능), 효율 랭킹은 같은 체급 안에서만 비교 (§12)

## 6. 서비스 메타데이터 취합 — 엑셀 (메타데이터 시트)

- 서비스·모델 표기 등 서비스 메타데이터는 **엑셀 양식("메타데이터 시트")으로 수기 취합**한다 (별도 시스템·등록 화면 없음, 취합 방식은 추후 변경 가능)
- 취합 항목: ① 서비스 표기(serviceGroup·service·담당자) ② 모델 canonical + alias 목록 + 파라미터 수(paramsB) ③ GPU 대시보드 할당 단위 매핑 ④ 소비 관계("A → B의 모델 M") ⑤ (플랫폼) 서비스 계정↔소비 서비스 매핑 ⑥ (케이스 A~C) `/metrics` URL
- 엔진 종류·버전은 `/v1/metrics` 응답의 `engine` 자기신고로 수신 — **수기 갱신 불필요**
- 미등록 모델 표기가 유입되면 담당자 확인을 거쳐 메타데이터 시트에 반영 (§5)

## 7. 모델별 GPU Hour 수집

**비용의 정본은 할당.** `서비스 일 비용 = 할당 GPU-hours(GPU 대시보드) × 기종별 단가` — 가동 여부와 무관하게 발생. 단가 단위는 **원/GPU·hour**(GPU 1장의 시간당 TCO).
`/v1/metrics`의 gpu 블록은 이 비용의 **용도 분해**: model × gpuType × category별로 **gpuCount(GPU 수)** 와 **gpuHours(= GPU 수 × 시간, 모델에 GPU가 매핑·할당된 시간)** 를 일별 제공. gpuType은 **단순 기종 표기**(A100, H100 등). gpuCount는 해당일 매핑된 GPU 수(하루 중 증감 시 최대 수 기준 — 실제 총량은 gpuHours가 표현). **모델 비용은 gpuHours × 기종 단가로만 계산**(gpuCount는 "몇 장 점유"의 표시·검증용). 하루 중 기종이 바뀌면 gpuType별로 행을 나눠 제공.

| category | 뜻 | 제공 주체 |
|---|---|---|
| `serving` | 프로덕션 서빙 | 서비스 |
| `standby` | HA 대기(failover) | 서비스 |
| `test` | 테스트·실험 (model unknown 허용) | 서비스 |
| (유휴) | 잔여 | **제공 안 함 — 중앙이 `할당 − Σ제공`으로 산출** |

- 정합성 검증: 기종별 Σ제공 gpuHours ≤ 할당 GPU-hours, 항목별 gpuHours ≤ gpuCount × 24, serving/standby의 model `unknown` 금지
- **효율 지표(원/1M토큰, 토큰/GPU-hour)는 serving만 사용** — HA 갖춘 팀이 비효율로 보이지 않도록. standby 비용·유휴율·활용률은 별도 지표
- **필수 준비**: GPU 대시보드 할당 단위(프로젝트/네임스페이스 등) ↔ service 매핑을 메타데이터 시트에 제출. 매핑 불가 시 제공 기반 폴백(단, 유휴 미포착 → 비용 과소계상 가능)
- 모델 교체·증설 이력은 daily 데이터에 자연 반영 — effective 필드 불필요. GPU 단가표 이력만 중앙이 관리

## 8. 사내 플랫폼을 쓰거나(소비자) 제공하는(공급자) 경우

**원칙 3가지**

1. **GPU Hour는 돌리는 쪽만 제공** (단일 제공 원칙) — 소비자는 플랫폼 사용분 GPU를 일절 제공하지 않음 (이중 계상 차단)
2. **소비자 식별은 공급자 책임** — 소비 서비스별 API 키(서비스 계정) 발급이 표준
3. 비용은 **발생한 곳(운영=공급자)과 유발한 곳(사용=소비자)** 두 관점으로 표시 — 어느 쪽으로 합쳐도 전사 총액 동일(검증 지표)

**수집·취합**

- 공급자: GPU 전량 + 토큰 제공(서비스 계정 userId로 소비자 구분) — **배부의 정본**
- 소비자: 플랫폼 사용분 GPU 제공 없음, 토큰 제공도 생략 권고 (자체 사용자 분석용으로 제공하더라도 전사 집계·배부에서는 제외)
- 취합 항목 2가지: **소비 관계**("A → B의 모델 M") + **서비스 계정↔소비 서비스 매핑**

**비용 배부**

- 공급자의 모델별 **serving 비용만** 소비자별 **가중 토큰(input×1 + output×4)** 비율로 배부 — 공급자 직접 트래픽도 하나의 소비자로 취급
- standby·test·유휴는 **배부하지 않음** → "플랫폼 오버헤드"로 공급자 귀속 (소비자가 통제 불가한 비용을 떠안기지 않기 위함)
- 표시: 소비자 화면 = 직접 비용 + 배부 비용 / 공급자 화면 = 총 운영비 + 소비자별 배부 내역 + 오버헤드
- **개인 직접 사용자**: user 단위로 귀속(기존 토큰 API에 이미 user 데이터가 있어 추가 수집 없음), 화면은 조직 rollup + 드릴다운. 미매핑 userId는 "미분류"로 표시·점검
- 성능(TTFT/ITL)은 공급자×모델 단위만 집계 — 소비자별 체감이 필요하면 소비자 게이트웨이에서 자체 측정 (측정 위치가 달라 엔진 수치와 단순 비교 금지)
- 하이브리드(자체 GPU + 플랫폼 병행): 자체분만 §7대로 제공, 플랫폼분은 배부로 합산. 다단계 소비 체인은 1단계에선 **1홉 제한** 권장

## 9. 성능 메트릭 — 내 케이스 찾기

지표: **TTFT**(요청→첫 토큰, ms) / **ITL**(토큰 간 간격, ms) — 각 p50·p90·p95·p99, **Output TPS**(tokens/s, p50만)

- percentile을 받는 이유: 평균은 느린 소수 요청을 가림 — 대다수 경험(p50)과 최악(p99) 구분
- RPS는 안 받음(기존 requests에서 파생 가능)
- 측정 위치 기준은 **추론 엔진** — 체감보다 낙관적일 수 있으나 전 서비스 동일 위치라 비교 성립

| 케이스 | 수집 경로 | 담당자 작업 | serving 블록 |
|---|---|---|---|
| A. vLLM | (b) 중앙 스크랩 | `/metrics` URL 제출 + 네트워크 개방 | 생략 |
| B. SGLang | (b) 중앙 스크랩 | 상동 (`--enable-metrics` 필요할 수 있음, 메트릭명 매핑 확인) | 생략 |
| C. 기타 Prometheus 엔진 (TGI 등) | (b) 우선 검토 | 상동 (+TTFT/ITL 매핑표 확정, 히스토그램 없으면 D로) | 생략 |
| D. 자체 구현 서빙 | (a) 자체 집계 | 스트리밍 시각 로깅 → daily p50/p90/p95/p99 집계 → GET 제공 | 채움 |
| E. 외부 API 연동 | (a) | `gpu: []`. 필요 시 게이트웨이에서 측정(측정 위치 명시). 외부 API 비용은 중앙이 토큰 단가로 별도 산출 | 선택 |
| F. 비스트리밍 | (a) | TTFT/ITL 개념 없음 — `e2eMs`(권장)·`custom[]`(선택)으로 제공 가능 | 선택 |

- **케이스 D 주의**: 레플리카 여러 대면 전체 로그를 모아 한 번에 percentile 계산 (레플리카별 p99의 평균 ≠ 전체 p99)
- 스크랩 경로(A~C) 특성: 히스토그램 버킷이라 레플리카 합산·주간/월간 p99 재계산 가능. 단, 스크랩 시작 이후 데이터만 존재(과거 소급 불가). 엔진 재시작은 중앙이 처리

## 10. API 계약 — GET /v1/metrics (기존 스펙 상속)

```
GET https://{service-host}/v1/metrics?date=YYYY-MM-DD   (KST 기준, 사내망·인증 없음)
```

| 상황 | 응답 |
|---|---|
| 확정 데이터 있음 | 200 + 본문 |
| 사용량·가동이 실제 0 | 200 + 빈 배열 |
| 아직 집계 전(미확정) | **409 — 빈 200 금지** ("0"과 "아직 없음" 구분) |
| 당일·미래 date | 400 |
| 보존 기간 초과 | 404 |

- `generatedAt`(+09:00) 포함, 같은 date 재호출 시 동일 결과 (재수집 안전)
- **필수**: date, serviceGroup, service, generatedAt, `gpu[]`(model·gpuType·gpuCount·gpuHours·category — 빈 배열 허용)
- **권장**: `engine {type, version}` 자기신고 / 플랫폼은 `serviceAccounts` 매핑(선택)
- `serving[]`은 경로(a) 팀만 채움. **토큰·requests 필드는 없음** (이중 소스 금지)

```json
{
  "date": "2026-08-18", "serviceGroup": "claude", "service": "claude-cowork",
  "generatedAt": "2026-08-19T01:30:00+09:00",
  "engine": { "type": "vllm", "version": "0.8.4" },
  "gpu": [
    { "model": "opus", "gpuType": "H100", "gpuCount": 4, "gpuHours": 96.0, "category": "serving" },
    { "model": "opus", "gpuType": "H100", "gpuCount": 1, "gpuHours": 24.0, "category": "standby" }
  ],
  "serving": []
}
```

## 11. 운영 규칙

- 중앙이 **02:00(KST)** 부터 전일 데이터 호출 시작 → 409면 1시간 간격 재시도
- 최근 **7일 backfill** 가능 — 정정 필요 시 서비스가 재집계 후 중앙에 재수집 요청
- 단위는 필드명에 명시(`Ms`·`gpuHours`·`Tps`) — 단위 착오 방지
- 스크랩 대상(A~C)은 (service, `/metrics` URL, 엔진 종류)을 메타데이터 시트에 제출 — service 라벨은 중앙이 스크랩 시 부여, 모델 라벨은 alias 사전으로 정규화

## 12. 이걸 하면 보게 되는 것 (중앙 계산 — 참고)

일 비용(할당 기준) · 활용률 · 유휴율 · 배부 비용 · **원/1M토큰** · 토큰/GPU-hour · standby 비용 · TTFT/ITL 추이 · **모델 채택도**(사용 서비스·사용자 수, 토큰 점유율 추세)
→ 서비스 상세는 `할당 → 용도 분해 → 성능 → 토큰 산출 → 비용·효율` 순의 표준 뷰로 통일 (효율 지표는 serving만, 성능은 서비스·모델 단위만)
→ **효율 랭킹은 체급(파라미터 기반 리그) 내에서만 표시** — 라지모델의 가치는 채택도(많은 서비스·사용자가 찾는다는 사실)로 강조. 품질 점수 축은 2단계 검토
